# Security

What protects this system, what does not yet, and why.

Sathiyaa holds identity documents, police verifications, medical certificates,
home addresses and the live location of people visiting elderly strangers at
home. That is the standard this is written against.

The second half of this document — **Known gaps** — is deliberate. Every one of
those is a decision somebody made on purpose, with a reason and a condition
that closes it. None of them is a surprise, and none of them should be "tidied
up" without reading why it is there first: two of them are load-bearing for
being able to sign in at all today.

---

## What is in place

### Authentication

| Who | How |
|---|---|
| Customer | mobile number + one-time code, bcrypt-hashed, with an expiry |
| Provider | mobile number + 6-digit PIN, bcrypt cost 10, plus device binding |
| Business partner | partner id / referral code / mobile / email, + password or one-time code |
| Administrator | email + password, bcrypt |

Tokens are JWTs, signed HS256, expiring after `JWT_EXPIRES_IN` (7 days by
default), carrying only `{role, id, name}`.

**Account enumeration is closed where it matters.** Nobody signs themselves up
as an administrator or a business partner, so those two sign-ins answer
identically whether the account does not exist or the password is wrong — and
take the same *time* to do it, by comparing against a real bcrypt hash of a
value nobody will ever type rather than returning early. Customer and provider
sign-in does say plainly that there is no account for a number, because the app
has to be able to offer to create one.

**Device binding.** A provider account is tied to the first handset that signs
in, and a second handset is refused. An administrator can release it from the
console when somebody genuinely changes phone. An account created in the office
is created *unbound*, so it binds to the provider's own handset rather than to
the office computer.

**PIN strength is enforced on every path that sets one** — six digits, not the
same digit six times, not `123456` or `654321`. The same three rules apply in
the app and in the admin console, from one function, so the console cannot be
the softer door.

### Authorisation

Every route is wrapped in `requireAuth(...roles)`; there is no endpoint that
infers who you are from the body. A provider's own endpoints read the id from
the token, never from a parameter, so there is no path where passing somebody
else's id does anything.

### What the console may see

`PROVIDER_COLUMNS` in `adminController.js` is an explicit column list, not
`SELECT *`, because `SELECT *` on that table was returning `pin_hash` to the
browser on every page load. Both the list and the create endpoint read through
one shared SELECT (`CONSOLE_PROVIDER_SELECT`) so a third handler cannot
reintroduce it. A PIN set by an administrator is never echoed in a response and
never written to the audit log — only the fact that staff set it.

### Input handling

- Every query is parameterised. The one place SQL is built from strings
  (`searchClause`) takes its table alias and column names from call-site
  literals and binds the search term; the term is also length-capped and has
  its LIKE wildcards escaped.
- Enum values are checked in `utils/enums.js` before they reach MySQL, because
  a value outside an ENUM is a 500 and "Something went wrong", not a refusal.
- Uploads are restricted by MIME type (JPEG, PNG, WebP, HEIC, PDF), capped at
  8 MB, written with a random filename that reveals nothing about the owner, and
  served with `X-Content-Type-Options: nosniff`.

### Transport and headers

Helmet, CORS restricted to configured origins, `trust proxy` set to a hop count
rather than `true` (trusting `X-Forwarded-For` blindly lets anyone walk around
the rate limiter one fake address at a time). TLS is terminated at CloudFront.

### Rate limiting

600 requests per 5 minutes generally; 20 per 15 minutes on sign-in and
code-request endpoints. Counting is **per IP and in memory**, which is correct
for one instance and wrong for several — if this ever runs behind a load
balancer with more than one box, move the store to Redis before trusting the
numbers.

### Refusing to start

`config/preflight.js` refuses to start a `PUBLIC_DEPLOYMENT` with no
`JWT_SECRET`, a placeholder one, one under 32 characters, an empty
`DB_PASSWORD`, an empty `CORS_ORIGINS`, or no `API_ACCESS_KEY`. Fatal, not a
warning: a forgeable token is the whole game, since anyone can sign their own
with `role: "admin"`.

### Audit log

Every state-changing action writes `audit_log` with the actor, their role,
their device and what they did. It is readable in the console and is the only
record of who approved, blocked or created what.

### Keeping secrets out of the repository

The repository is generated by `scripts/sync-to-github.mjs` from an allowlist,
and every copied file is scanned for the live secret values — read at run time
from a file that is never published — plus seven patterns for AWS keys, private
key blocks, Razorpay and Stripe live keys, Google API keys, and GitHub and
Slack tokens. A hit aborts the sync before anything is staged.

## Known gaps

Each of these is deliberate. Each says what closes it.

### 1. One-time codes are returned in the API response

**What.** While `NODE_ENV` is not `production`, requesting a code returns it in
the response body as `devOtp`.

**Why it is there.** No SMS provider is wired up. Without this, nobody could
sign in at all — not a tester, not the client, not a demonstration. It is the
single thing holding the current deployment together.

**What it means.** Anybody holding the API access key can sign in as any
registered mobile number. The access key is therefore a password, and must not
appear in a public repository, a screenshot or a support ticket.

**What closes it.** Configuring an SMS provider and setting
`NODE_ENV=production`. The code path is already there —
`integrations/providers/sms.js` — and `devOtpField()` returns nothing the
moment `isProd` is true. **No code change is needed; this closes on
configuration alone.**

Preflight prints this as a warning on every public start, so it cannot be
forgotten.

### 2. The API access key is readable by anyone who has an APK

**What.** `API_ACCESS_KEY` is compiled into both apps and into the console
bundle.

**Why it is there.** It is a door on the building, not a lock on the safe. What
it stops is an unauthenticated scanner finding the hostname and walking through
a registration flow that hands back one-time codes — which, given gap 1, is an
open account. It costs one header and it is honest about what it is.

**What it means.** Anyone who unpacks an APK can read it. It is not and never
was an authentication mechanism.

**What closes it.** Gap 1 closing removes most of what the key is protecting
against. After that it stays as cheap noise-reduction, or goes.

### 3. Uploaded documents are served without authentication

**What.** `/uploads/...` sits above the access-key check and has no
authorisation of its own. Anyone with the URL can fetch the file.

**Why it is there.** The admin console renders these with `<img src>`, which
cannot send an `Authorization` header, and every URL already stored in the
database is a bare path. Putting the path behind a check would break every
image in the console and both apps at once.

**What protects it today.** The filename is sixteen random bytes and is handed
only to people entitled to the file — a capability URL. Responses are now
`Cache-Control: private` (they were `public, max-age=604800`, which let
CloudFront and any corporate proxy store somebody's Aadhaar card in a shared
cache) and carry `X-Robots-Tag: noindex, nofollow`.

**What it means.** A capability URL is weaker than an access check in two
specific ways: a URL that leaks stays valid forever, and nothing records who
fetched it.

**What closes it.** Moving storage to S3 and handing out pre-signed URLs with a
short expiry. That is a change inside `controllers/uploadController.js` plus
one resolver in each client (`uploadUrl()` in the console, `absoluteUrl()` in
both apps) — the seam is already there, which is why the uploader's own comment
says swapping the storage engine touches no caller. **This is the most
significant item on this list and should be done before the first real
customer's documents are stored.**

### 4. Tokens cannot be revoked

**What.** A JWT is valid until it expires. Blocking an account stops new
sign-ins; it does not invalidate a token already issued.

**Why it is there.** No session table. Stateless tokens were the right call for
the size of this system and remain so for most of it.

**What it means.** Blocking somebody leaves them working for up to
`JWT_EXPIRES_IN`. The console's own "change my password" screen says this
plainly, and says that changing `JWT_SECRET` and restarting is the way to cut
every session short immediately.

**What closes it.** Either a short expiry with refresh tokens, or a
`token_version` integer on each account included in the token and compared on
each request — the second is about thirty lines and no new table. Worth doing
when there is a real reason to eject somebody quickly.

### 5. No lockout after repeated wrong PINs

**What.** A wrong PIN is refused and counted by the rate limiter, but the
account itself is never locked.

**Why it is there.** Twenty attempts per fifteen minutes per IP is already far
below what a dictionary attack needs against a six-digit PIN, and locking
accounts on failed attempts is itself a denial-of-service against the person
who owns the account — a carer locked out mid-shift cannot start a visit.

**What it means.** A patient attacker with many addresses has more room than a
lockout would give them.

**What closes it.** Per-account attempt counting with a short cool-off, in
addition to the per-IP limit — not instead of it. Worth doing alongside gap 4.

### 6. No payment gateway

**What.** Payments are stubbed. `transactions` rows are written, nothing is
charged.

**Why it is there.** No merchant account yet. The Razorpay implementation is
written and sits behind the same interface as the stub.

**What it means.** No number on any screen represents money that moved. The
customer app says so on the screen where a card would be charged.

**What closes it.** Credentials and `PAYMENT_PROVIDER=razorpay`. Webhook
signature verification must be reviewed before that goes live — it is written
but has never run against a real callback.

### 7. Rate limiting is per-process

Described above; repeated here because it is a gap, not a feature. One instance
today. Move the store to Redis before a second one.

### 8. Face matching is written but not enabled

AWS Rekognition (`docs/AWS-REKOGNITION.md`) needs an IAM key pair. Until then
`facial_recognition_verified` is set by a stub that always passes, so the
start-of-service identity check currently proves nothing. The OTP check beside
it is real.
