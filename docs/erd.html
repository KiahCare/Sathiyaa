01 — the mechanismOne booking, many offers, first acceptance wins

This is the part of the design that everything else hangs off, and the part a column list can't show you. A customer doesn't pick a provider. They describe a need; the server works out who qualifies and offers the job to all of them at once.

02 — stateWhat a booking moves through

Seven states on bookings.status. Each arrow is an action by a named party, and each one writes an audit_log row.

Seven joins have no foreign key, deliberately. Anyone writing a query against these needs to know they will not be caught by the database: transactions, audit_log and otp_log are polymorphic — their reference_id / user_id means a different table depending on the *_type column beside it. customers.referred_by_code joins a partner by code string, not id. approved_by and updated_by point at admin_users, and booking_payments.recorded_by at a provider, without a constraint. user_devices.user_id joins this list: it means one of four tables depending on user_type. That is 44 enforced keys and eight you must get right yourself.

What is deliberately not real yet

  • Payments — no gateway. The tables and the flow exist; confirming records the charge and moves on. Nothing is debited.
  • SMS — OTPs appear on screen instead of being sent. No provider, no bill.
  • Push notifications — the apps poll every 20 seconds instead.
  • Face matching — the arrival photo is genuinely taken, uploaded and stored against the booking. The automated comparison is off.
  • Masked calls — the provider sees and dials the real number. Masking needs a paid telephony account.

Each of those is a provider-selector swap, not a rewrite: the adapter is stubbed by default and an environment variable points it at a real one. The schema already carries the columns each would fill.

Where this stood, and where it stands. The earlier version of this page warned that the schema had not been checked against the two reference apps, and that anything they asked for which this model did not hold — a chat thread, booking on somebody else's behalf — would be new tables rather than a tweak. That was exactly right, and those tables now exist: migrations 008 to 011 added the device registry, the dependent on a booking, emergency alerts and the message thread. What is still unchecked against the reference build is anything to do with subscriptions or shift rosters.

09 — addedThree tables that answer questions the schema could not

Added 19 September, in migrations 008 to 011. Each one exists because something the platform needed to be able to say afterwards had nowhere to be written down.

TableKeyWhat it holds
user_devices user_type + user_id + device_id Every handset an account has signed in from: make, model, OS version, app version, whether it is a real device or an emulator, first and last seen, and the address the request came from. No foreign key, deliberately — user_id points at one of four tables depending on user_type, which a constraint cannot express; the joins live in the admin controller instead. A table rather than more columns on the account, because the question worth answering after something goes wrong is "which devices has this account been on", and a single column cannot answer it.
sos_alerts → customer_id, booking_id One row per emergency raised, written before any message is attempted — a gateway that is down must not lose the fact that somebody pressed the button. delivery distinguishes simulated from sent, which is what lets the app be honest on screen when no SMS provider is configured. recipients is JSON because it is a list of who-and-what-happened and nothing queries inside it. acknowledged_at and resolution are how the office closes one, and a blank resolution is refused.
booking_messages → booking_id The thread on a booking, read from both ends. sender_type includes system, so the app's own notes — visit started, running late — sit in the same sequence rather than having to be merged with events from elsewhere. read_at null means unread, which is what drives both badges. Tied to a booking rather than an open inbox: an open messaging surface between strangers on a care platform is a safeguarding problem, and the booking is what makes the conversation legitimate.

Migration 009 added no table. It added bookings.for_family_member_id — nullable, pointing at customer_family_members — so a booking can be for somebody other than the person who made it. NULL means "for the account holder", which keeps every row written before it correct without a backfill, and is what every screen keys off. It also gave family members a date_of_birth and a notes column, because a carer visiting somebody needs to know how old they are and whether to knock twice.
